### [Feat] 그룹 채팅 기능 전체 구현

---

#### 기획 배경

기존에는 1:1 채팅만 있었다. 동행 신청이 수락되면 해당 동행 참여자들이 하나의 채팅방에서 소통할 수 있어야 한다는 요구가 있었다.

**설계 원칙:**
- 기존 1:1 채팅 로직과 테이블을 건드리지 않는다
- WebSocket 엔드포인트 `/chattingSock`을 재사용하되 `isGroupMessage` 플래그로 분기
- 동행 수락 즉시 자동으로 그룹방이 생성되도록 연동
- 동일 동행에 두 번째 신청자가 수락되어도 방이 중복 생성되지 않는 멱등 구조

---

#### DB 설계

4개의 신규 테이블을 기존 테이블과 완전히 분리해서 생성했다.

```
COMPANION_BOARD (기존)
    ↓ FK
GROUP_CHAT_ROOM       — 방 (동행 당 1개)
    ↓ FK
GROUP_CHAT_MEMBER     — 참여자 (UK: 방+회원 복합)
GROUP_MESSAGE         — 메시지
GROUP_MSG_READ        — 읽음 워터마크 (LAST_READ_MSG 컬럼)
```

**읽음 처리 방식 — 워터마크 패턴**

일반적인 읽음 테이블은 메시지마다 1행씩 생성하지만, 규모가 커지면 비효율적이다.
대신 사용자별로 "마지막으로 읽은 메시지 번호"만 저장한다.

```sql
-- 미읽음 = 내 워터마크보다 번호가 큰 메시지 수
SELECT COUNT(*) FROM GROUP_MESSAGE
WHERE GROUP_ROOM_NO = #{roomNo}
  AND GROUP_MSG_NO > NVL((SELECT LAST_READ_MSG FROM GROUP_MSG_READ ...), 0)
```

신규 메시지가 아무리 많아도 GROUP_MSG_READ 행은 멤버 수만큼만 유지된다.

#### 백엔드 구현

**GroupChatServiceImpl — 멱등 방 생성**

동행 수락이 여러 번 발생해도(N명 수락) 채팅방은 1개만 생성되어야 한다.
`selectGroupRoomNoByCompanionNo`로 기존 방 존재 여부를 먼저 확인하고,
멤버 추가 시 UK 중복 오류는 `DuplicateKeyException`으로 흡수한다.

```java
Integer existingRoomNo = groupChatMapper.selectGroupRoomNoByCompanionNo(companionNo);
int groupRoomNo;

if (existingRoomNo == null) {
    // 방 신규 생성
    GroupChatRoomDTO room = GroupChatRoomDTO.builder()
            .companionNo(companionNo).roomName(roomName).build();
    groupChatMapper.insertGroupRoom(room);   // selectKey로 PK 선취
    groupRoomNo = room.getGroupRoomNo();
} else {
    groupRoomNo = existingRoomNo;            // 기존 방 재사용
}

for (int memberNo : memberNos) {
    try {
        groupChatMapper.insertGroupMember(groupRoomNo, memberNo);
    } catch (DuplicateKeyException e) {
        // 이미 멤버인 경우 무시
    }
}
```

**group-chat-mapper.xml — 읽음 UPSERT**

Oracle `MERGE`를 활용해 INSERT/UPDATE를 한 번에 처리한다.
`lastReadMsg = 0` 전달 시 현재 방의 최신 메시지 번호로 자동 설정되도록 SQL 안에 분기를 뒀다.

```xml
MERGE INTO GROUP_MSG_READ dst
USING (SELECT #{groupRoomNo} AS GROUP_ROOM_NO, #{memberNo} AS MEMBER_NO,
           CASE WHEN #{lastReadMsg} = 0
                THEN NVL((SELECT MAX(GROUP_MSG_NO) FROM GROUP_MESSAGE
                          WHERE GROUP_ROOM_NO = #{groupRoomNo}), 0)
                ELSE #{lastReadMsg}
           END AS LAST_READ_MSG
       FROM DUAL) src
ON (dst.GROUP_ROOM_NO = src.GROUP_ROOM_NO AND dst.MEMBER_NO = src.MEMBER_NO)
WHEN MATCHED THEN
    UPDATE SET dst.LAST_READ_MSG = src.LAST_READ_MSG
WHEN NOT MATCHED THEN
    INSERT (READ_ID, GROUP_ROOM_NO, MEMBER_NO, LAST_READ_MSG)
    VALUES (SEQ_GROUP_READ_ID.NEXTVAL, src.GROUP_ROOM_NO, src.MEMBER_NO, src.LAST_READ_MSG)
```

**ChattingWebSocketHandler — isGroupMessage 분기**

기존 `handleTextMessage`에서 `MessageDTO`로 바로 파싱하던 것을 `JsonNode`로 먼저 읽어 플래그를 확인하는 방식으로 변경했다. 기존 1:1 경로 코드는 한 줄도 건드리지 않았다.

```java
JsonNode root = objectMapper.readTree(message.getPayload());
boolean isGroup = root.has("isGroupMessage") && root.get("isGroupMessage").asBoolean();

if (isGroup) {
    handleGroupMessage(senderNo, root);   // 신규: 방 멤버 전체 브로드캐스트
} else {
    handleDirectMessage(senderNo, root);  // 기존 로직 그대로
}
```

**CompanionServiceImpl — 수락 시 그룹방 자동 생성**

`updateJoinStatus`의 승인(A) 처리 블록 끝에 그룹방 생성 호출을 추가했다.
채팅방 생성 실패가 수락 트랜잭션을 롤백해서는 안 되므로 별도 try-catch로 감쌌다.

if ("A".equals(status)) {

    }
}

#### 프론트엔드 구현

**GroupMessageDTO — isGroupMessage Jackson 직렬화**

Java에서 `boolean isGroupMessage` 필드는 Lombok이 `isGroupMessage()` getter를 생성하고,
Jackson이 이를 `groupMessage`로 직렬화해 프론트에서 `isGroupMessage`를 못 읽는 문제가 있다.

`@JsonProperty("isGroupMessage")`를 명시하고 필드명을 `groupMessage`로 선언해 해결했다.

```java
@Builder.Default
@JsonProperty("isGroupMessage")
private boolean groupMessage = true;
```

**ChatPanel.jsx — 탭 구조**

`selectedRoom`이나 `selectedGroupRoom`이 설정된 상태(채팅 중)에서는 탭을 숨기고,
방 목록 보기 상태에서만 탭 바를 표시한다.

```jsx
const isInRoom = !!(selectedRoom || selectedGroupRoom);

// 탭 바 — 룸 미선택 상태에서만 표시
{!isInRoom && (
  <div className="flex border-b border-slate-200">
    <button onClick={() => setActiveTab('direct')}>1:1 채팅</button>
    <button onClick={() => setActiveTab('group')}>그룹 채팅</button>
  </div>
)}
```

WebSocket 수신 분기도 추가했다. `isGroupMessage` 플래그에 따라 다른 React Query 캐시를 invalidate한다.

```js
const handleWsMessage = useCallback((msg) => {
  if (msg.isGroupMessage) {
    // 그룹 메시지
    queryClient.invalidateQueries({ queryKey: ['groupMessages', groupRoomNo] });
    markGroupReadMutation.mutate({ groupRoomNo, lastReadMsgNo: msg.groupMsgNo });
    queryClient.invalidateQueries({ queryKey: ['groupChattingRooms'] });
  } else {
    // 1:1 메시지 — 기존 로직 그대로
    queryClient.invalidateQueries({ queryKey: ['messages', chattingRoomNo] });
    updateReadMutation.mutate(chattingRoomNo);
    queryClient.invalidateQueries({ queryKey: ['chattingRooms'] });
  }
}, [...]);
```

### [Fix] 배포 후 JS 모듈 MIME 오류

---

#### 증상

배포 직후 브라우저 콘솔에 다음 에러가 연속 발생하며 앱이 로드되지 않았다.

```
Failed to load module script: Expected a JavaScript-or-Wasm module script
but the server responded with a MIME type of "text/html".
Strict MIME type checking is enforced for module scripts per HTML spec.

Uncaught TypeError: Failed to fetch dynamically imported module:
https://hondi.site/assets/Login-Bn7i94cf.js
```

---

#### 원인 분석

서버에는 새 빌드 파일(`Login-Do77eBK7.js`)이 정상 업로드되었다.
그런데 브라우저는 이전 배포 때 캐시한 구버전 `index.html`을 그대로 사용하고 있었고,
구버전 `index.html`은 이미 삭제된 구버전 JS 파일(`Login-Bn7i94cf.js`)을 참조하고 있었다.

**흐름:**

```
브라우저 캐시의 구버전 index.html
    ↓ <script src="/assets/Login-Bn7i94cf.js"> 로드 시도
서버: /assets/Login-Bn7i94cf.js 없음 → try_files 폴백 → index.html 반환 (text/html)
    ↓
브라우저: JS 모듈로 요청했는데 text/html 응답 → MIME 오류 → 앱 로드 실패
```

Vite는 빌드마다 파일명에 해시값을 붙이므로(`Login-[hash].js`) 매 배포 시 파일명이 바뀐다.
따라서 구버전 `index.html`을 캐시에서 쓰면 반드시 이 문제가 발생한다.

---

#### 해결

`index.html`에 `Cache-Control: no-cache` 헤더를 설정해 브라우저가 항상 서버에서 최신본을 가져오도록 했다.

**nginx.conf 수정:**

```nginx
# 변경 전
location / {
    root /home/ec2-user/dist;
    index index.html;
    try_files $uri $uri/ /index.html;
}

# 변경 후
location / {
    root /home/ec2-user/dist;
    index index.html;
    try_files $uri $uri/ /index.html;
    add_header Cache-Control "no-cache, no-store, must-revalidate";
    add_header Pragma "no-cache";
    add_header Expires 0;
}
```

`no-store`까지 추가한 이유: `no-cache`만으로는 캐시에 저장은 하되 재검증을 강제하는데,
일부 오래된 브라우저나 프록시가 이를 무시하는 경우가 있다.
`no-store`는 캐시 저장 자체를 금지하므로 가장 확실하다.

단, 이 헤더는 `/` location 전체에 적용된다. `/assets/` 하위의 JS/CSS 파일들은
이미 파일명에 해시가 포함되어 있어 내용이 바뀌면 URL 자체가 바뀌므로 캐싱해도 안전하다.
필요하다면 추후 `/assets/` 경로에 `Cache-Control: public, max-age=31536000, immutable`을 별도 설정할 수 있다.

---

| 파일 | 내용 |
|------|------|
| EC2: `/etc/nginx/nginx.conf` | `location /`에 Cache-Control no-cache 헤더 추가 |

### [Fix] 백엔드 미배포로 인한 API 404

---

#### 증상

백엔드 배포 없이 프론트엔드만 배포한 뒤 브라우저 콘솔에 다음 에러가 반복 발생했다.

```
GET https://hondi.site/api/group-chatting/rooms 404 (Not Found)
```

React Query의 `refetchInterval: 5000` 설정으로 인해 5초마다 요청이 반복되어 콘솔이 도배됐다.

---

#### 원인 분석

EC2에서 실행 중인 Spring Boot JAR는 이번 작업 이전에 빌드된 **구버전**이었다.
`GroupChattingController`는 이번에 새로 작성한 클래스이므로 구버전 JAR에는 존재하지 않는다.

```
로컬 코드         EC2 실행 중인 JAR
    ↓                   ↓
GroupChattingController  없음 → /api/group-chatting/* 모두 404
```

프론트엔드 배포(SCP → nginx reload)와 백엔드 배포(JAR 빌드 → 업로드 → 재시작)는 **독립된 작업**인데,
프론트만 배포하고 백엔드를 누락한 것이다.

---

#### 해결

**1단계 — 로컬 Gradle 빌드**

```bash
./gradlew bootJar
# → build/libs/backend-0.0.1-SNAPSHOT.jar 생성
```

**2단계 — EC2로 JAR 업로드**

```bash
scp backend-0.0.1-SNAPSHOT.jar ec2-user@52.78.65.4:/home/ec2-user/
```

**3단계 — 기존 프로세스 종료 및 재시작**

구버전 프로세스가 8080 포트를 점유하고 있어 `kill PID`만으로는 즉시 해제되지 않았다.
`fuser -k 8080/tcp`로 포트 기준 강제 종료 후 새 JAR를 실행했다.

```bash
fuser -k 8080/tcp
sleep 2
nohup java -jar /home/ec2-user/backend-0.0.1-SNAPSHOT.jar \
  --spring.profiles.active=prod > /home/ec2-user/app.log 2>&1 &
```

약 8초 후 `Tomcat started on port 8080` 확인.

---

#### 재발 방지

백엔드 코드 변경이 있을 때는 프론트엔드 배포와 **별도로** 아래 순서를 반드시 실행해야 한다.

| 순서 | 명령 | 설명 |
|------|------|------|
| 1 | `./gradlew bootJar` | 로컬 빌드 |
| 2 | `scp ... backend-*.jar ec2-user@...` | EC2 업로드 |
| 3 | `fuser -k 8080/tcp` | 기존 프로세스 종료 |
| 4 | `nohup java -jar ... &` | 새 JAR 실행 |
| 5 | `tail -f app.log` | 기동 로그 확인 |

---

#### 파일 변경

| 대상 | 내용 |
|------|------|
| EC2: `/home/ec2-user/backend-0.0.1-SNAPSHOT.jar` | 신규 빌드 JAR로 교체 |
