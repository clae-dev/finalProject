### [Feat] 리뷰 목록 — 검색 + 정렬 기능 추가

---

#### 기획 배경

자유게시판엔 검색창이 있고, 숙소 목록엔 이름/주소 필터가 있는데 **리뷰 목록만 페이지네이션 외에 아무 필터가 없었다.**

후기가 쌓일수록 "내가 찾던 여행지 후기"를 찾기 어려워지는 문제. 검색과 정렬은 목록 페이지의 기본 UX인데 빠져있던 것.

---

#### 변경 흐름

```
사용자 입력 (검색어 / 정렬 선택)
    ↓
Reviews.jsx — 상태 관리 + UI
    ↓
useReview.ts — React Query 훅 (queryKey에 search, sort 포함)
    ↓
reviewAPI.ts — GET /api/reviews?search=제주&sort=rating_desc
    ↓
CompanionReviewController.java — @RequestParam 수신
    ↓
CompanionReviewServiceImpl.java — 파라미터 전달
    ↓
CompanionReviewMapper.java + XML — 동적 SQL 처리
```

프론트부터 DB까지 전 레이어를 수정했다.

#### 프론트엔드 — reviewAPI.ts

**변경 전:**

```ts
export const getReviewList = async (page = 1, size = 9) => {
  const response = await axiosApi.get("/api/reviews", { params: { page, size } });
  return response.data;
};
```

**변경 후:**

```ts
export const getReviewList = async (
  page = 1, size = 9,
  search = '', sort = 'latest'
) => {
  const params: Record<string, unknown> = { page, size };
  if (search) params.search = search;
  if (sort && sort !== 'latest') params.sort = sort;
  const response = await axiosApi.get("/api/reviews", { params });
  return response.data;
};
```

`search`가 빈 문자열이면 파라미터 자체를 안 보내도록 처리. `sort`도 기본값(`latest`)이면 생략 — 기존 API와 호환성을 유지하면서 선택적으로 파라미터를 추가하는 방식.

---

#### 프론트엔드 — useReview.ts

```ts
// 변경 전
export const useReviews = (page = 1, size = 9) => {
  return useQuery({
    queryKey: ['reviews', page, size],
    queryFn: () => getReviewList(page, size),
  });
};

// 변경 후
export const useReviews = (page = 1, size = 9, search = '', sort = 'latest') => {
  return useQuery({
    queryKey: ['reviews', page, size, search, sort],
    queryFn: () => getReviewList(page, size, search, sort),
  });
};
```

`queryKey`에 `search`와 `sort`를 포함시키는 게 핵심.

> **React Query queryKey 역할:**
> queryKey가 바뀌면 React Query가 새로운 요청으로 인식하고 다시 fetch한다.
> 만약 queryKey에 search를 안 넣으면, 검색어를 바꿔도 캐시된 이전 결과를 그대로 반환해버린다.

#### 프론트엔드 — Reviews.jsx

**추가된 상태값:**

```js
const [searchInput, setSearchInput] = useState(''); // 입력창 텍스트
```

`searchInput`과 `search`를 분리한 이유:
- `searchInput` — 키보드 입력마다 바뀌는 입력창 상태
- `search` — 실제로 API를 호출할 때 쓰는 값, 검색 버튼을 눌러야 적용

만약 하나로 합치면 글자를 칠 때마다 API가 호출되어 서버에 과부하가 걸린다.

**검색 처리:**

```js
const handleSearch = (e) => {
  e.preventDefault();
  setSearch(searchInput.trim());
  setCurrentPage(1); // 검색 시 1페이지로 리셋
};
```

정렬 변경 시에도 동일하게 1페이지로 리셋:

```js
const handleSortChange = (value) => {
  setSort(value);
  setCurrentPage(1);
};
```

**UI 구성:**

```
[ 🔍 제목이나 내용으로 검색  ×  검색 ]  [ ≡ 최신순 | 별점↑ | 별점↓ ]  [ + 후기 작성 ]
```

검색 결과가 있을 때는 상단에 안내 텍스트 표시:

```

```

빈 상태도 상황에 맞게 분기:
- 검색 결과 없을 때: "검색 결과가 없습니다" + 검색 초기화 버튼
- 데이터 자체 없을 때: "아직 후기가 없습니다" + 첫 후기 작성 버튼

```java
        @RequestParam(defaultValue = "latest") String sort)
```

기본값을 지정했기 때문에 기존 프론트엔드 코드나 다른 곳에서 파라미터 없이 호출해도 정상 동작한다.

---

#### 백엔드 — MyBatis XML (핵심)

**`selectReviewList` — 동적 ORDER BY:**

```xml
ROW_NUMBER() OVER (ORDER BY
    <choose>
        <when test="sort == 'rating_desc'">R.RATING DESC, R.CREATED_AT DESC</when>
        <when test="sort == 'rating_asc'">R.RATING ASC, R.CREATED_AT DESC</when>
        <otherwise>R.CREATED_AT DESC</otherwise>
    </choose>
) AS RN
```

**`selectReviewList` + `selectReviewCount` — 동적 WHERE:**

```xml
WHERE R.STATUS = 'Y'
<if test="search != null and search != ''">
    AND (UPPER(R.TITLE)   LIKE '%' || UPPER(#{search}) || '%'
      OR UPPER(R.CONTENT) LIKE '%' || UPPER(#{search}) || '%')
</if>
```

**`<choose>`를 사용한 이유:**

ORDER BY 절에는 `#{}`(prepared statement 바인딩)을 사용할 수 없다. DB가 파라미터를 **값**으로만 처리하기 때문에 컬럼명이나 정렬 방향에 바인딩하면 에러가 난다.

그래서 `${sort}`(문자열 직접 치환)을 쓰는 방법도 있지만, 이건 SQL Injection에 취약하다. 사용자가 `sort='; DROP TABLE COMPANION_REVIEW; --` 같은 값을 보내면 그대로 쿼리에 박힌다.

`<choose>`로 허용된 값만 분기하는 방식이 가장 안전하다. 모르는 값이 들어오면 `<otherwise>`의 기본 정렬로 처리.

**`UPPER()` 처리 이유:**

```sql
UPPER(R.TITLE) LIKE '%' || UPPER(#{search}) || '%'
```

오라클 DB는 기본적으로 대소문자를 구분한다. "제주"와 "JEJU"처럼 한글 검색에선 크게 상관없지만, 영문이 포함된 제목을 검색할 때 "jeju"로 검색해도 "JEJU" 제목의 후기가 잡히게 하기 위해 양쪽을 `UPPER()`로 통일.

### [Feat] 동행 글 수정 기능 추가

---

#### 기획 배경

동행 게시판에 Create(작성), Read(상세), Delete(삭제)는 있었는데 **Update(수정)만 없었다.**

CRUD 중 하나가 빠져있으면 포트폴리오에서 눈에 띈다. 특히 동행 모집 특성상 날짜나 인원이 바뀌는 경우가 잦은데, 지금 구조로는 삭제 후 재작성만 가능했다.

---

#### 변경 흐름

```
사용자 (수정 버튼 클릭)
    ↓
CompanionDetail.jsx — 수정 버튼 → /companions/:id/edit 이동
    ↓
CompanionEdit.jsx — 기존 데이터 pre-fill, 이미지 관리
    ↓
useCompanion.ts — useUpdateCompanion 훅 → FormData 전송
    ↓
companionAPI.ts — PUT /api/companions/:id (multipart/form-data)
    ↓
CompanionController.java — @PutMapping("/{no}")
    ↓
CompanionServiceImpl.java — 이미지 처리 (keep + new 합산)
    ↓
companion-mapper.xml — UPDATE COMPANION_BOARD WHERE ... AND MEMBER_NO = #{memberNo}
```

#### 이미지 관리 — 핵심 설계

수정 폼에서 이미지 처리가 제일 복잡하다. 경우의 수가 세 가지다:

| 상황 | 처리 방법 |
|------|-----------|
| 기존 이미지 유지 | URL 문자열 그대로 `keepImages`에 담아 전송 |
| 기존 이미지 삭제 | X 버튼 클릭 → `existingImageUrls` 배열에서 제거 (전송 안 됨) |
| 새 이미지 추가 | `newImageFiles` 배열에 File 객체 추가 → `newImages`로 전송 |

프론트엔드에서는 두 종류의 상태로 분리해서 관리:

```js
const [existingImageUrls, setExistingImageUrls] = useState([]); // 기존 이미지 URL 목록
const [newImageFiles, setNewImageFiles] = useState([]);          // 새로 추가할 File 객체
const [newImagePreviews, setNewImagePreviews] = useState([]);    // 새 이미지 미리보기 URL
```

백엔드에서도 같은 방식으로 합산:

```java
// 1. keepImages(기존 유지 URL)를 쉼표로 split해서 allImages에 추가
// 2. newImages(새 파일)를 UUID 리네임 후 저장하고 allImages에 추가
// 3. allImages를 쉼표로 join → contentImages 컬럼에 저장
companion.setContentImages(allImages.isEmpty() ? null : String.join(",", allImages));
```

#### 기존 데이터 pre-fill

수정 폼에 진입하면 `useCompanionDetail`로 기존 게시글 데이터를 가져와서 폼에 자동 입력한다.

```js
useEffect(() => {
  if (companion && !initialized) {
    setForm({
      title: companion.title || '',
      content: companion.content || '',
      travelDate: companion.travelDate?.match(/(\d{4}-\d{2}-\d{2})/)?.[1] || '',
      maxMembers: companion.maxMembers || 4,
      tags: companion.tags || '',
    });
    if (companion.contentImages) {
      setExistingImageUrls(
        companion.contentImages.split(',').map(s => s.trim()).filter(Boolean)
      );
    }
    setInitialized(true); // 두 번 실행 방지
  }
}, [companion, initialized]);
```

`initialized` 플래그를 쓰는 이유: `companion` 데이터가 바뀔 때마다 useEffect가 실행되는데, 사용자가 이미 입력한 내용을 덮어쓰면 안 되기 때문이다. 최초 1회만 채우고 그 이후는 무시한다.

`travelDate` 처리도 주의 포인트. 백엔드가 `YYYY-MM-DD HH24:MI` 형식으로 내려주는데 `<input type="date">`는 `YYYY-MM-DD`만 받는다. 정규식으로 앞 10자만 추출:

```js
companion.travelDate?.match(/(\d{4}-\d{2}-\d{2})/)?.[1] || ''
```

#### 작성자 권한 체크

수정은 작성자만 할 수 있어야 한다. **프론트와 백엔드 양쪽에서 동시에 막는다.**

**프론트 (CompanionEdit.jsx):**

```js
const isAuthor = user && companion && Number(user.memberNo) === Number(companion.memberNo);

if (!isLoading && companion && !isAuthor) {
  return <수정 권한 없음 화면>;
}
```

**백엔드 (companion-mapper.xml):**

```xml
WHERE COMPANION_NO = #{companionNo}
  AND MEMBER_NO    = #{memberNo}
```

`AND MEMBER_NO = #{memberNo}` 조건이 있기 때문에, 다른 사람의 글 번호로 PUT 요청을 보내도 UPDATE 0건으로 처리된다. 0건이면 Controller에서 403 반환.

프론트에서 막더라도 백엔드를 직접 호출하는 공격에는 무력하다. 그래서 둘 다 막아야 진짜 안전하다.

#### FormData로 multipart 전송

이미지 파일을 함께 보내야 하므로 `application/json`이 아닌 `multipart/form-data`로 전송한다.

```js
const handleSubmit = async (e) => {
  e.preventDefault();
  const fd = new FormData();
  fd.append('title', form.title);
  fd.append('content', form.content);
  // ... 나머지 텍스트 필드

  // 기존 유지 이미지: URL을 쉼표로 이어서 하나의 문자열로
  if (existingImageUrls.length > 0) {
    fd.append('keepImages', existingImageUrls.join(','));
  }

  // 새 이미지: File 객체를 각각 append
  newImageFiles.forEach(file => fd.append('newImages', file));

  await updateMutation.mutateAsync(fd);
};
```

백엔드에서 `keepImages`는 `@RequestParam String`으로 받고, `newImages`는 `@RequestParam List<MultipartFile>`로 받는다.
